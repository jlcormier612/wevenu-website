# Manager Permissions Release Readiness — Assessment

Phase 5 of the platform's release-readiness review. Booking Financial Architecture, Seating, and Key Dates are closed (Almost Ready, Almost Ready, Not Ready). This assessment covers the team-role permission system — Owner / Manager / Coordinator / Staff, built on `venue_staff` — judged by attempting to actually break its trust boundaries, not by reading what it's supposed to do.

## Methodology

This phase required a different kind of live test than the previous three: proving a permission boundary holds means actually holding the lesser-privileged credential and trying to do the thing it shouldn't be able to do. With the user's explicit authorization, two real second Supabase Auth accounts were created and walked through the actual invitation flow — a real invite email's URL token, real `/join`-equivalent RPC acceptance, landing as a genuinely active `manager` and a genuinely active `staff` team member on the real venue. Every test below was run as that credential, hitting the same RLS-protected tables and RPCs the real app uses — not as the venue owner, and not as a superuser. Where a raw API call was used in place of clicking a UI button, it was to answer the specific question the button's existence doesn't answer on its own: if the button weren't there, or were bypassed, would the database still say no? All test data — two auth accounts, four `venue_staff` rows, one client, one event, one invoice, one payment schedule, one payment line item, one relationship record — was created through real paths and fully removed; final checks confirm the roster is back to exactly the one real owner and both test logins are confirmed dead.

## What Held Up Well

**The self-referencing-RLS-plus-RETURNING hazard that broke `venues` earlier in this codebase's history does not reproduce on `venue_staff`, despite having the same suspicious shape.** `venue_staff`'s own SELECT policy calls `current_user_venue_id()`, which itself queries `venue_staff` — structurally similar to the confirmed `venues` bug. Live-tested: inviting a team member via the real `.insert().select().single()` pattern (`lib/team/service.ts:117-131`) succeeded cleanly, HTTP 201, correct row returned. The reason it's safe here and wasn't safe there: the inserting user's own venue resolution depends on their *own*, already-existing `venue_staff` row, not on the row being freshly inserted — there's no true circular read against the row that doesn't exist yet, unlike the `venues` case. Worth documenting precisely so this exact shape of pattern-matching doesn't get flagged as a false positive again.

**Self-escalation is genuinely blocked, at the database layer, not just in the UI.** Live-tested three ways as an active Manager: attempting to promote their own row to `owner` (0 rows affected — the RLS `with check` clause rejects it silently), attempting to promote a Staff member directly to `manager` (explicit `403`, RLS policy violation), and attempting to touch the real owner's `venue_staff` row at all, e.g. deactivating it (0 rows affected). All three are backed by the RLS policy itself, not just `canManageStaff()`'s application-layer check — a real, working defense-in-depth.

**A venue cannot be accidentally stranded without an owner.** No code path exists to change, remove, or deactivate the owner's own row — confirmed by the same live tests above plus the `venues_update` `with check` clause, which structurally cannot move `owner_user_id` away from the current owner via any UPDATE.

**Every financial-deletion action that the permission model documents as owner/manager-only is actually backed by RLS, not just app code** — contract deletion, payment-line-item deletion, and payment-schedule deletion all have a matching `current_user_role() in ('owner','manager')` clause in their DELETE policies, confirmed by direct migration read. This is the correct pattern; it's the *absence* of this same pattern elsewhere that's the core finding below.

## Architecture Issues

These are trust-boundary violations, live-demonstrated, not incomplete features. Each represents a place where a stated security guarantee of this system — "only an owner can do X," "only the invited person can accept," "RLS is the real backstop" — does not actually hold when tested directly against the database rather than through the UI.

**1. The owner-only refund guard has no RLS backstop — a live-tested bypass.** `refundLineItem_` (`lib/payments/service.ts:271-292`) is the only place in the app that checks role before a refund, and it's owner-only. But the actual `payment_line_items_update`/`payment_schedules_update` RLS policies have no role clause at all — just `venue_id = current_user_venue_id()`. Live-tested: authenticated as a real, active Manager, a raw `PATCH` directly against `payment_line_items` — setting `status: 'refunded'`, `refunded_amount: 5000` — succeeded outright, HTTP 200, and the refund was real and persisted. This is the one financial action in the whole system where the app-layer check and the RLS layer disagree; every sibling action (delete contract, delete payment item, delete schedule) has both layers in agreement. A second test, as an active Staff member, confirmed the blast radius is bounded correctly by Postgres's own RLS semantics — because Staff is excluded from the SELECT policy on this table, and Postgres requires SELECT-policy visibility as a precondition for UPDATE even when the UPDATE policy itself doesn't restrict it, Staff's identical attempt affected zero rows. So the exposure is specifically Manager and Coordinator (both of whom retain full financial visibility) — still real, still live, still bypassing a rule the product explicitly states.

**2. RLS provides no role differentiation at all for the vast majority of the venue's operational data — confirmed with a live hard-delete as Staff.** The TR-G1 migration that built role-based RLS only touched contracts, payments/invoices, and `venue_staff` itself. Roughly forty other tables — `clients`, `events`, `leads`, `floor_plans`, `documents`, `packages`, `playbook_templates`, and more — were swept into `venue_id = current_user_venue_id()` RLS with zero role clause, and no service function anywhere in those areas calls the role-check helper either. Live-tested as an active Staff member (the most junior role, the one role explicitly excluded from financial visibility): a raw `PATCH` edited a client's guest count directly, and a raw `DELETE` hard-deleted that client outright — both succeeded, no error, no role check anywhere in the path. Hard-deleting a client isn't even a capability the app's own UI exposes to *anyone*, owner included — there is no delete-client feature in the product at all — which makes this worse, not better: the only way this capability is reachable is by going around the UI entirely, and when you do, there's no permission check waiting for you. (A compounding detail found in the same test: the hard-delete also left an orphaned Event and Invoice behind, `client_id` silently nulled by the foreign key rather than cascading — a data-integrity side effect of a capability that was never meant to be reachable in the first place.)

**3. The invite-token binding has no identity check — live-demonstrated to let the wrong person claim an invite.** `accept_team_invitation` matches purely on the token in the URL; it never compares the accepting session's email to the `venue_staff.email` the invite was addressed to. Live test: an invite was created for `unclaimed.invitee@example.com` as `coordinator`. It was then accepted while logged in as the already-existing, unrelated Manager test account — and it succeeded. The Manager account is now simultaneously a `manager` row and a `coordinator` row at the same venue, both active, both correctly resolvable back to one real person. This proves two compounding problems: first, if an invite link is ever forwarded, guessed, left in a shared inbox, or reused, whoever holds it — not whoever it was addressed to — gets the access; second, once a single user does hold two roles at one venue, `current_user_role()` has no `ORDER BY` on its underlying query, so which of the two roles actually governs a given request is Postgres's arbitrary choice, not a designed invariant. In this test it happened to resolve to `manager`; nothing guarantees it always would.

## Product Completion Items

None of these are security violations — the RLS layer holds where it's supposed to for these. They're gaps between what the permission model promises and what a coordinator actually experiences.

1. **Every role sees the same team-management UI**, regardless of what they can actually do — the invite form, the role-change menu, and financial action buttons (like Refund) render identically for Owner, Manager, Coordinator, and Staff alike. Restrictions are only discovered after clicking, via a server-rejection toast. Confirmed the UI never over-*grants* (every gated button is correctly backed server-side, per the Architecture section above, except refund/core-object mutation which fail for the reason already documented there) — the gap is purely that the UI doesn't communicate the boundary up front.
2. **`/settings/team`'s own page copy is stale**: "Only the owner can invite or remove members" has been factually wrong since Manager-level invite/remove shipped for staff/coordinator targets.
3. **The roster page shows every team member's full name, email, and role to every active team member of any role**, including Staff — the permission model's own proposal document describes Coordinator/Staff as "view own profile only," which was never built.
4. **`updateStaffRole` silently no-ops when targeting the owner's row** instead of returning a clear "you can't do that" — it filters the owner out of the update, gets zero rows affected and no database error, and returns `{ok: true}` anyway. Functionally harmless (confirmed above — the owner truly is untouched) but a misleading success signal if anyone ever surfaces that return value to a user.

## Engineering Cleanup Items

1. **`venue_staff.role = 'owner'` and `venue_staff.is_owner = true` are two independently-writable representations of the same fact**, with nothing keeping them in sync. Real authority is derived from `venues.owner_user_id`, not either of these columns, so a drift between them is cosmetic (a wrong badge in the roster UI) rather than a privilege change — but it's the same "two copies of one fact, no cross-check" pattern already found repeatedly in this review series.
2. **`venue_staff` has no DELETE grant for any database role at all — not even `service_role`** — removal is soft-delete (`is_active = false`) only, by design. Worth confirming this is intentional rather than an oversight, since it also meant this audit's own cleanup required a direct superuser connection rather than the normal API path any other cleanup in this review series has used.
3. **`venue_users` (the TR-G3 compatibility view over `venue_staff`)** is real and actively depended on by roughly a dozen subsystems (budget, RSVP, seating, documents, feedback, Luv), but inherits none of TR-G1's role-gating — it only ever exposes `is_active`, never role. Not a live bug today, but any future policy written against `venue_users` needs the same scrutiny this audit gave `venue_staff` directly, since it won't inherit it automatically.

## Recommendation: **Not Ready**

This is a different severity class from the previous three phases. Booking Financial Architecture and Seating were sound systems with real, scoped product gaps; Key Dates was a correctly-built feature with a missing wire. Manager Permissions is a security boundary, and live testing found three places — not hypothetical, actually exercised with a real second account — where that boundary doesn't hold: a Manager can refund money the product says only an Owner can refund, a Staff member can hard-delete a client with zero permission check of any kind, and an invite link grants access to whoever holds it rather than whoever it was sent to. None of these require rethinking the permission model itself — the model (four roles, RLS as the real backstop, app-layer checks as a UX convenience) is sound where it was actually applied. The problem is coverage: TR-G1 closed the specific line items in its own scope and stopped there, leaving the broader promise — that RLS is the backstop for role restrictions — true for financial deletion and false almost everywhere else, including the one case (refund) where it mattered most.

This is exactly the kind of finding the review was designed to surface before launch, not after. Closing it is three scoped, well-understood additions (a role clause on two UPDATE policies, a role clause swept across the ~40 untouched tables per the original documented matrix, an email-match check in one RPC) — not a redesign.

### Prioritized Findings

1. **[Architecture / Blocker] No RLS backstop on refunds** — Manager and Coordinator can bypass the owner-only refund rule via a direct API call, live-confirmed.
2. **[Architecture / Blocker] No role differentiation on ~40 core-data tables** — any active team member, including Staff, can create/edit/hard-delete clients, events, leads, floor plans, documents, and more, live-confirmed with a real client hard-delete.
3. **[Architecture / Blocker] Invite acceptance has no identity check** — any authenticated user holding the token URL can claim the invite regardless of the email it was addressed to, live-confirmed, and the resulting multi-role state resolves non-deterministically.
4. **[Product Completion] Role-based UI restrictions don't exist** — every role sees the same team-management and financial-action affordances; restrictions surface only as after-the-fact server errors.
5. **[Product Completion] Stale permission copy and unbuilt roster-visibility restriction** — page text and the "view own profile only" behavior described in the permission model were never implemented.
6. **[Product Completion] Silent no-op on owner role-change attempts** — harmless today, but a misleading success signal.
7. **[Engineering Cleanup] `role`/`is_owner` drift potential, `venue_staff`'s delete-proof schema, and `venue_users`'s inherited-gating gap** — none live-exploitable today, all worth tracking.
