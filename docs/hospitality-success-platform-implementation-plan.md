# Hospitality Success Platform — Implementation Plan

**Program 3 — Customer Success & Growth Platform, Initiative A.** Planning only — no implementation until this plan and the open questions in §7 are approved. Companion to `docs/hospitality-success-platform-assessment.md`, which this plan builds directly on rather than re-deriving.

**Date:** 2026-07-22

---

## 0. The organizing principle: a journey, not a wizard

This is the one idea every pillar below has to reinforce, so it's stated once, up front, rather than repeated as decoration in each section.

**The difference is not tone — it's what the software claims to be doing.** A wizard configures settings. A journey opens a business. Concretely, that means:

- Every step names the venue, not "your venue" — "Let's set the hours couples can tour **Willow Creek**," not "Configure business hours."
- Every step is framed as a hospitality outcome the venue is enabling, not a technical action being performed — "Let's make sure couples can pay you online," not "Connect Stripe."
- Progress is never lost and never anonymous. The moment a venue tells the platform its name, that name should be usable everywhere — the greeting, the setup steps, Luv's voice, the completion moments.
- Nothing is ever a dead end. Every screen answers "what should I do next," even the empty ones.
- Completion is celebrated, briefly and warmly, then the venue keeps working — never a full-screen "Achievement Unlocked" moment that gets in the way.

**This requires one concrete technical change that doesn't exist today**: the pre-creation setup wizard has to stop being pure client-memory. A journey that forgets your venue's name the moment you close the tab isn't a journey. §1 below makes this the first architectural decision in Guided Setup, not an afterthought.

**Voice ownership**: this initiative treats Luv as the narrator of the entire journey, not just the Success Guide pillar. The Getting Started/Guided Setup copy, the Migration Center's status language, and Luv's Success Library's framing should all read as if Luv is the one saying them — because per the assessment, Luv's established voice, tone settings (`LuvSettings.preferredTone`), and celebration mechanism (`celebrateLuv()`) already exist and are the correct place for this language to live, not a separate copywriting layer bolted onto each pillar independently.

**Added 2026-07-22 — Luv is a companion, not documentation.** This is a hard rule, not a stylistic preference, and it constrains every piece of copy this initiative produces:

- Luv never *points at* an answer. She *does it with you*. Never "Here's our article about Tour Scheduling." Always something closer to: *"I see you haven't set your tour hours yet — that's why your booking link isn't offering appointments. It'll take about three minutes. Ready? I'll stay with you while we do it."*
- Concretely, this means every Guided Setup gap and every Luv's Success Library surfacing needs two things an article link alone doesn't have: (1) a diagnosis — *why* this matters right now, stated as a specific consequence ("that's why your booking link isn't offering appointments"), not a generic feature description, and (2) an offer to act together — a CTA that starts the task itself (opens the relevant step/screen with Luv's presence carried into it), not a CTA that opens a help article in a new context and leaves the venue to figure out the rest alone.
- Luv's Success Library articles still exist (§4) — they're the deep-reference material for someone who wants to read further — but they are never the *first* thing Luv offers for an unfinished setup gap. The first offer is always "let's do this together"; the article is the secondary "want to read more first" option, not the primary response.
- This changes what "linking to the relevant article" (§1.2, §3.2, §4.2) actually means in practice: the primary link target for a setup gap is the task itself, with Luv's diagnosis copy attached; the Success Library article is a secondary, clearly-labeled "read more" affordance alongside it, never the only response.

## 1. Guided Setup

### 1.1 The central decision: reconcile, don't add a fourth system

Per the assessment, three systems already answer some version of "what's next" and don't share data: the Getting Started checklist, the Activation Engine, and Luv's proactive observations. Guided Setup's job is to become the **one** system a venue experiences, built by wiring these together — not a fourth parallel one.

**Architecture:**

- **Activation Engine remains the source of truth for "what's missing" and "how far along is this venue."** Its 5-dimension, 100-point, gap-producing model (`compute_venue_activation_score()`) is already the most rigorous of the three. Getting Started's ad hoc TypeScript checks (`computeOnboarding()`) get retired as a separate computation and become a **presentation layer over Activation's own gaps** — same underlying data, framed as a journey rather than a score. Concretely: `ActivationGap { label, points, href }` becomes the input to a new `GuidedSetupStep` view model that adds the journey framing (why this matters, estimated time, prerequisites, success criteria) as static copy keyed by gap/milestone id — not a second computation.
- **The post-creation flow keeps its current entry point** (Dashboard, `#getting-started` anchor) but the card itself is rebuilt on top of Activation's gaps instead of `computeOnboarding()`'s independent field checks. This also finally fixes the phase-label drift the assessment found between the design doc and the shipped SQL — one score, one set of labels, everywhere.
- **Luv's observation feed gains a new observation source**: setup gaps become `recommendation`-kind `LuvObservation`s (`lib/luv/types.ts`'s existing contract), generated by reading Activation's gaps — not recomputing them — exactly matching the "read, never recompute" rule the assessment found already governs how Luv treats Event Readiness and Communication Health. This is what makes "I noticed your website isn't collecting inquiries yet" and "Nobody can currently schedule a tour" (your own examples) actually work: they're just gap-to-observation translations of data that already exists, surfaced through Luv's already-established voice.
- **`DashboardLuvIntro`'s one-shot boolean gate stays** (it's a fine, simple mechanism) but its trigger condition changes from "has this flag ever been set" to something that actually reflects a new venue — tied to the venue's `created_at` recency and/or activation phase being `"setup"`, not a permanent flag alone.

### 1.2 The pre-creation wizard becomes resumable and named

This is the one piece of Guided Setup that's a genuine build, not a reconciliation:

- **Persist a minimal venue row earlier than today.** Today nothing exists in the database until the final "Create venue" submit. The plan: create a real (but `setup_completed: false`) `venues` row as soon as the venue's name is captured (end of the current "Venue information" step), then every subsequent step becomes an `update`, not accumulating client state toward one big insert. This is the single change that makes "Let's get Willow Creek ready" possible from step 2 onward instead of only after the whole wizard finishes.
- The wizard's step components, validation (`lib/venue/validation.ts`), and field UI stay — this is additive persistence underneath existing steps, not a rewrite of the steps themselves.
- Abandoning and returning resumes at the first incomplete step, computed the same way Activation/Getting Started already compute "is this filled in" (profile completeness check, etc.) — reusing, not reinventing, that logic.
- Per-step copy gains the four elements your brief asked for (explanation, estimated time, prerequisites, success criteria) — `post-setup-financial.tsx`'s existing explanatory-paragraph pattern is the template; the Financial Setup step itself gets folded into this same resumable step sequence rather than remaining a separate post-creation screen glued on with a `?financial=1` query param.

### 1.2a Persona-based onboarding — added 2026-07-22

The journey is not one script. Three distinct venue situations get a distinct opening and a distinct emphasis, chosen explicitly rather than inferred:

- **Brand-new venue** — teach everything. The full step sequence, every "why this matters" explanation shown at full length, no assumption of prior software experience.
- **Existing venue switching from another (non-Weven) system** — the same step sequence, but Migration Center is surfaced early and prominently ("Let's import your current weddings" becomes one of the first steps offered, not something discovered later in Settings), and per-step copy leans on "bring this over" language rather than "set this up from scratch" language.
- **Former Weven customer** — a distinct opening tone specifically because of shared history, not just a migration emphasis: *"Welcome back. We're excited to have you with us again. We'll make this transition as smooth as possible, and we'll help bring over the information you need so you can get back to serving your couples."* This acknowledges the history and the trust already earned without dwelling on why they're switching, and gets the same migration-forward step ordering as the general-switching persona.

**Architecture**: a single early micro-question, right alongside the venue-name capture that already anchors step 2 onward (§1.2) — *"Is this a brand-new venue, or are you bringing an existing business onto Hello to Cheers?"*, with a second question only for the second answer ("Are you coming from Weven, or somewhere else?"). Stored as `venues.onboarding_persona text check (in ('new','switching','weven_returning'))`, set once, changeable later from Settings if picked wrong (never a silent, permanent lock-in). This one column is what every persona-varying piece of copy in Guided Setup and Luv's voice reads to select which script it's using — a single source of truth, not a persona flag re-derived independently in three places.

### 1.3 What does NOT change

- The underlying `venues` table shape, `complete_venue_setup` RPC's role for *validating* a complete setup, and the Activation Engine's SQL scoring logic are not being redesigned — this plan extends how they're presented and sequenced, not what they compute.
- QuickBooks/Stripe connect flows (already real, already good per the recent Sprint 4 work) are reused exactly as built; Guided Setup only changes the surrounding narrative and step sequencing they're presented in.

### Status (2026-07-22) — §1 complete

Most of §1.1 and all of §1.2/§1.2a had already shipped earlier in this same engagement, discovered live rather than assumed when this pass began: `computeOnboarding()` no longer exists (`buildGuidedSetupChecklist()` in `lib/dashboard/service.ts` already presents `activationScore.checklist` directly — the phase-label drift is already gone), the wizard is already resumable (`saveSetupProgressAction`/`setup_last_step`/sticky-once-true `setup_completed`), and `onboarding_persona`/`OriginStep` already exist. This pass closed the three pieces that were genuinely still open:

- **Luv's setup-gap observation source** — `lib/luv/setup-observations.ts`'s `computeSetupGapObservations()`, a pure function reading `activationScore.checklist` (never recomputing), producing up to 3 `recommendation`-kind `LuvObservation`s for the highest-point incomplete items, reusing the same `GAP_COPY` diagnosis text the Getting Started card already shows (extracted to `lib/dashboard/gap-copy.ts` so both surfaces read one copy table, not two). Wired into `getDashboardData()`'s `luvObservations` array, gated by the same `observationsEnabled` setting every other Luv source respects. Live-verified against the real seeded venue's actual `compute_venue_activation_score()` output.
- **`DashboardLuvIntro`'s trigger condition** — was a permanent one-shot flag only (`!venue.luvIntroSeenAt`); now also requires the venue to actually look new (`activationScore.phase === "setup"` or created within 14 days), so a mature venue that simply never dismissed the card doesn't have it resurface.
- **Financial Setup folded into the main step sequence** — the "payments" step (previously an inert, disabled Stripe placeholder) now embeds the real `QuickBooksConnectSection`/`StripeConnectSection` components, server-fetched via a new `getPaymentsStepDataAction()` (session-scoped, no venue id needs threading through wizard state — by the time a venue reaches step 6 of 7, `saveSetupProgressAction` has already persisted a real row). The separate post-creation `?financial=1` screen (`PostSetupFinancial`) is gone from the routing entirely; its "your venue is ready" congratulations moment moved inline into `setup-wizard.tsx` as the `handleSubmit()` success state, reached immediately after "review"'s "Create venue" submit. Both OAuth callbacks (`/api/quickbooks/callback`, `/api/stripe/callback`) updated to redirect back to plain `/setup` for `returnTo=onboarding` (was `/setup?financial=1` for QuickBooks; Stripe's callback had no `returnTo` concept at all before this and always went to `/settings`, which would have silently stranded anyone connecting Stripe from the new "payments" step — given the same `state = "{venueId}:{returnTo}"` treatment as QuickBooks already had). Since `setup_completed` is still `false` while on "payments" (finalization only happens at "review", one step later), the existing resumability logic naturally lands the browser back on "payments" with no new state needed.

`tsc --noEmit` and `next build` both clean. Not verified in a live browser (this environment has none) — the OAuth redirect changes in particular are traced through carefully but unexercised end-to-end pending real Stripe/QuickBooks credentials, same posture as this engagement's other OAuth work (TR-M1, the QuickBooks Online Launch Integration).

## 2. Migration Center

### 2.1 Extend the existing import wizard; do not replace it

Per the assessment, `/settings/import` is real and good. The plan adds, in priority order:

1. **A batch/job identity.** New column `import_batch_id uuid` on every importable entity table (or a lighter join-table alternative if adding a column to five tables is judged too invasive — see open question in §7), generated once per wizard run and stamped on every row it creates. This single addition is what unlocks: "what's already been imported" progress tracking as distinct runs, a real "view past imports" history, and rollback (a batch delete scoped to `import_batch_id` where nothing downstream depends on the row yet — see the rollback scoping note below).
2. **Duplicate detection for the other four entities**, porting `findActiveDuplicate()`'s exact shape (venue-scoped, active-status-only where the entity has a status concept, email-then-name fallback) to Clients first (the highest-stakes entity for "migrating your whole business"), then Vendors/Packages/Inventory.
3. **Claim the two dormant hooks the assessment found**: `TrustTier`'s unused `"import"` value becomes the real trust tier CSV/migration imports log under (replacing the current `"manual"` mislabeling), and `lead_intake_attempts.status`'s dormant `"rejected_duplicate_batch"` value gets a real code path — a within-file duplicate (two rows in the same CSV describing the same person) rejected at the batch level, distinct from an against-the-database duplicate.
4. **AI-assisted field mapping** for genuinely unfamiliar competitor-export column headers — extending Luv's existing import-assist family (`lib/luv/import-assist.ts`'s direct-Claude-call pattern) from "structure this unstructured text" to "suggest which of my columns maps to which of your fields," surfaced as a pre-filled suggestion in the existing field-mapping step, always reviewable/overridable before any write (matching every other Luv-assist surface's "proposal only, never auto-committed" rule).
5. **Rollback, scoped conservatively.** A batch is only cleanly reversible while nothing else in the system has touched the records it created (no payments recorded against an imported client, no messages sent to an imported lead, etc.). The plan: rollback is offered only within a short window and only if a batch-level check finds zero downstream activity on every row in the batch — otherwise the venue sees "this import can no longer be automatically undone; here's what changed and when" rather than a broken partial rollback. This preserves the assessment's flagged concern (rollback is a real commitment, not a small add) by being honest about when it's actually safe, rather than promising universal undo.

**Status (2026-07-22) — all 5 items complete.** Items 1, 2, and 5 turned out to already be built (`import_batch_id` on all 5 entity tables, `findActiveDuplicate*` for all 5, and a window-limited `rollbackImportBatch` — found live rather than assumed when this pass began). Items 3 and 4 were genuinely still open and closed in this pass:

- **Item 3, both dormant hooks, real bugs closed, not just labels fixed.** `TrustTier`'s `"import"` value existed in the type but every CSV-imported lead's `lead_intake_attempts` row was silently mislabeled `trust_tier: "manual"` — `createLeadCore` (`lib/leads/service.ts`) hardcoded it regardless of caller. Fixed by threading an explicit `trustTier` parameter through `createLead`/`createLeadForVenue` (defaulting to `"manual"` for the single-lead-add form, the one caller that should keep it), with both `importLeadsAction` and `importLeadsForVenueAction` now passing `"import"`. Separately, within-file duplicate detection (two rows in the same CSV describing the same person) didn't exist at all — only against-the-database checks did. Added a stable in-memory `leadIdentityKey()` (mirrors `findActiveDuplicate()`'s own email-then-name matching exactly) tracked per import run in both action files; a repeat key logs a real `lead_intake_attempts` row via the new `logDuplicateBatchRejection()` (`lib/lead-intake/pipeline.ts`), transitioning it straight to the schema's long-dormant `rejected_duplicate_batch` status. One real bug found live while wiring this: `lead_intake_attempts.source` is a foreign key into the registered `lead_sources` vocabulary, not free text — an initial `"csv_import"` literal violated the constraint; fixed to reuse the row's own already-resolved `source` field (`row.source || "other"`), the same resolution `createLeadCore` already does for a real create. Both the identity-key matching and the full insert→`rejected_duplicate_batch` transition were live-verified against the real database.
- **Item 4, AI-assisted field mapping.** New `proposeFieldMapping(headers, entity)` (`lib/luv/import-assist.ts`), same direct-Claude-call pattern as `proposeStructuredRows` right above it — given a CSV's actual headers and the target entity's field schema, asks Claude which header best matches which field, defensively rejecting any hallucinated header not actually present in the real list (verified with a synthetic response exercising exactly this case) or field key outside the entity's real schema. Surfaced in the field-mapping step (`components/settings/import-wizard.tsx`'s `StepMapFields`) as a "Suggest with Luv" button, shown only when unmapped fields remain after the existing lowercase-similarity auto-match — merges suggestions in as fill-only for still-empty fields, never overwriting a mapping already set, with a toast telling the coordinator to review before continuing. One action (`proposeFieldMappingAction`) serves both the self-service and White-Glove entry points, since no venue context is needed for a stateless mapping suggestion.

Not verified against a real Anthropic API call (`ANTHROPIC_API_KEY` isn't configured in this environment) — same posture as every other Claude-dependent feature in this codebase; the response-parsing/defensive-filtering logic itself was verified against a synthetic Claude-shaped response. `tsc --noEmit` and `next build` both clean.

### 2.2 White-glove (staff-assisted) migration — one platform, two audiences, both in v1

**Decided 2026-07-22: white-glove ships together with self-service, not as a fast-follow.** During beta and early acquisition, many venues will choose or switch to staff-assisted implementation — the internal tooling has to exist from day one so staff can safely complete migrations, resume a venue's partially-completed self-service setup, correct imported data, and finish implementations without ever touching the database directly.

This changes the architecture from "self-service wizard, plus a separate staff capability bolted on" to a genuinely shared platform:

- **One migration engine, one data model, two entry points.** The wizard steps, field mapping, dry-run preview, duplicate detection, batch tracking, and rollback logic (§2.1) are not reimplemented for staff — the exact same server actions and validation run whether the session initiating them is a venue owner or an HQ staff member. The only thing that differs by audience is *which capabilities are available* and *whose venue_id the action is scoped to*.
- **Role-based capability, not two codepaths.** A venue user can only ever act on their own venue (unchanged, existing RLS). An HQ staff member, from within an active View-As session, gets a new, real, audited write capability scoped specifically to migration/setup actions — the same "Import on behalf of this venue" and "resume/correct this venue's setup" actions a venue user has, exercised on the venue's behalf, every action logged against the staff member's own identity (extending View-As's existing `hq.view_as` engagement-event audit pattern, not inventing a new audit mechanism).
- **This is real new RLS infrastructure, deliberately narrower than general impersonation.** It covers the migration/import tables and the Guided Setup resumable-state added in §1.2 (so staff can pick up a setup a venue started, not just run imports) — it does not become a general "HQ can write anything as any venue" capability. If staff-assisted work is later needed beyond setup/migration (e.g., staff editing a venue's live booking data), that's the larger, still-deferred Phase 2 impersonation work named in `docs/wevenu-hq-architecture.md` — genuinely out of scope here, and this plan does not build toward it by accident.
- **Real architectural finding, discovered live during implementation (2026-07-22), that changes how this gets built**: the original assumption — that white-glove could call the exact same repository insert functions self-service uses, just with `createAdminClient()` (service_role) and an explicit `venueId` instead of one resolved from session — holds for Packages and Inventory (plain inserts, genuinely parameterized), but **not** for Clients or Vendors. `insertClient`/`insertVendor` both call RPCs (`create_client_atomic`, `create_vendor_atomic` — confirmed live to be `security invoker`, not `security definer` as first assumed; corrected here) that resolve the venue via `current_user_venue_id()` **internally**, ignoring whatever `venueId` was passed in. Neither RPC granted `EXECUTE` to `service_role` either.
- **Shipped and live-verified (2026-07-22)**: `supabase/migrations/20261141000000_white_glove_atomic_venue_override.sql` adds a guarded `p_venue_id_override uuid default null` parameter to both RPCs, honored **only** when `auth.role() = 'service_role'` — an authenticated venue session can pass this parameter too, but it's silently ignored for them (falls back to their own `current_user_venue_id()` exactly as before). Also found and fixed live in the same pass: `venue_customer_relationships`/`venue_vendor_relationships` were missing the `service_role` table grants these RPCs need as `security invoker` functions (a `security invoker` RPC only ever has the privileges of whoever's actually calling it — the RPC's own `EXECUTE` grant doesn't imply the underlying table grants exist). Verified against the real local DB, not assumed: (1) a real `service_role` call with an explicit override venue id inserts into that exact venue, for both Client and Vendor; (2) a real `authenticated` venue-owner session attempting the same override with a foreign/bogus venue id has it silently ignored — the row lands in the caller's own real venue, no hijack path exists; (3) a plain call with no override (every existing self-service call site, unchanged) behaves identically to before. This is the one blocking piece; the repository-layer wiring (an explicit admin-client + venueId path through `insertClient`/`insertVendor`) and the staff-facing UI below are next.
- **Staff-facing surface**: see the new §2.2a below — this was originally sketched as a small addition to the Beta Command Center's venue table, but the user's 2026-07-22 direction reframes it as a first-class internal tool in its own right, not a privileged view of the self-service wizard.
- **Correction, not just import**: because staff need to fix already-imported data (not only run fresh imports), the review/duplicate-resolution workflow (§2.1 item 2's dedup, and the dry-run preview's error list) needs to support being revisited after the fact — editing a previously-imported row's mapped values or resolving a flagged duplicate post-import — rather than only being a one-time pre-write gate. This is an extension of the existing preview/results step UI, not a new screen.

### 2.2a The Customer Success Workspace — White-Glove as a first-class internal tool

**Added 2026-07-22, per explicit user direction**: *"The White-Glove experience is not just a privileged version of Migration Center. It should feel like an internal Customer Success workspace. Optimize it for Jennifer and future onboarding specialists."* This reframes §2.2's staff-facing surface from "a venues-by-status table bolted onto Beta Command Center" into its own workspace, purpose-built around what an onboarding specialist actually does all day: work several venues' onboardings concurrently, in and out of focus over days, with visible blockers and a paper trail.

**What already exists in `app/admin/*` and is reused, not rebuilt** (per `docs/wevenu-hq-architecture.md`, confirmed live by reading the code, not assumed):
- `hq_admins` / `current_hq_admin_role()` / `getHqAdmin()` — staff identity and role gate. No new auth system needed.
- `venue_hq_notes`, `venue_hq_tasks`, `venue_hq_crm_state` — internal notes, follow-up tasks, and last/next-contact cadence, already per-venue, already audited by author. **Blockers reuse `venue_hq_tasks` with one added column** (`kind text default 'task' check (kind in ('task','blocker'))`) rather than a new table — a blocker is structurally a task (title, due date, completed/resolved) that simply needs a distinct visual treatment and to roll up into cross-account counts; inventing a parallel table for something this close would violate this codebase's own "don't duplicate a system that already does 90% of the job" discipline.
- `recordEngagementEvent()` with `actor_type: 'hq_admin'` — the audit mechanism every staff-initiated action (View-As, notes, and now migration writes) already logs through.
- The `*_hq_select` RLS pattern (ten policies already shipped) — the precedent §2.3's new `*_hq_write` policies extend, not a new mechanism.
- **View-As is currently read-only by design** (`docs/wevenu-hq-architecture.md` §2.5, explicit Phase 1 scope) — general in-app impersonation is a deliberately deferred, much larger project. White-glove does **not** build that. It builds a narrower, audited **write capability scoped specifically to migration/setup actions**, reusing View-As's session/banner UX but never expanding to arbitrary app-wide writes — this boundary is restated from §2.2 because it's the thing most likely to scope-creep into "just build real impersonation" if not held firm.

**What's genuinely new — the Onboarding Engagement, one layer above a single import run:**

A single `import_batches` row (§2.3) already tracks one CSV/paste run. It does not track "Jennifer is three days into onboarding Willow Creek, currently paused, waiting on the venue for a vendor list, with two open blockers." That's a session-spanning case file, not an import run, and needs its own record:

- New table `venue_onboarding_engagements` — `id, venue_id (unique — one engagement per venue, not per attempt), assigned_hq_admin_id, status ('not_started' | 'in_progress' | 'paused' | 'blocked' | 'complete'), current_focus text (free-text, "importing vendor list"), started_at, paused_at, resumed_at, completed_at, created_at, updated_at`. `status` is staff-set, not inferred — an onboarding specialist explicitly pauses/resumes/marks-blocked rather than the system guessing from inactivity, matching this codebase's "system proposes, human confirms" convention used everywhere else (Activation gaps, Luv observations).
- Every `import_batches` row and every `venue_hq_tasks` (blocker-kind) row for a venue optionally links to that venue's current `venue_onboarding_engagements.id` — so "what did Jennifer do during this engagement" is answerable directly, not reconstructed by timestamp-guessing across unrelated tables.
- **Pause/resume is a status + timestamp pair, not a soft-delete or a separate table** — same "status column, not parallel state machine" discipline as `payment_schedules`' Needs-Review status ([[booking-financial-architecture-initiative]]) and Event Order's Open/Finalized/Amended lifecycle. Resuming just flips `status` back to `in_progress` and stamps `resumed_at`; history of pause/resume cycles, if ever needed for reporting, comes from the engagement-event audit log already recording every staff action, not a bespoke log on this table.

**Cross-account dashboard** (`/admin/onboarding`, new top-level HQ nav item — restores "Customer Success" as its own nav pillar per the original `wevenu-hq-architecture.md` §1 IA sketch, which reserved this exact spot but folded it into venue-detail pages when nothing justified a standalone surface yet):
- One row per venue with an engagement: venue name, assigned specialist, status badge (reusing `components/hq/health-badge.tsx`'s badge shape, new status vocabulary), open blocker count, days since last activity, current focus. Same "list view → row click → full detail page" convention as the Beta Command Center venue table (§2.2 of `wevenu-hq-architecture.md`), not a new interaction pattern.
- Filterable/sortable by status and by assigned specialist — a specialist's own "my venues" view is just this table filtered to `assigned_hq_admin_id = me`, not a separate screen.

**Per-venue workspace** (`/admin/onboarding/[venueId]`) — the actual place Jennifer spends her day:
- Header: venue name, status, assigned specialist (reassignable), Start/Pause/Resume/Mark Complete controls (each an audited action).
- The exact same Migration Center wizard a venue would run themselves, rendered here in an explicit "Importing for {venue}" state (reusing View-As's persistent-banner convention), writing through the same server actions with the new `service_role` + `p_venue_id_override` path from §2.2's shipped fix.
- Guided Setup resumability status (§1.2's resumable venue row) — so a specialist picking up a venue's partially-completed self-service setup sees exactly which step it stopped at, not a blank slate.
- Blockers & Notes — the existing `SupportSection` shape (`components/hq/venue-detail/support-section.tsx`), extended to show blocker-kind tasks with their own visual weight (an open blocker is the one thing that should be impossible to miss on this page), reused as-is for plain notes.
- **Communicate with the venue — scoped narrowly for v1.** No bidirectional in-app messaging thread between HQ staff and a venue exists anywhere in this codebase today (Conversations is venue↔couple/vendor/lead only) — building one is a real, separate messaging-infrastructure project, not a checkbox inside this workspace. **v1 recommendation**: a "Send an update" action that composes and sends a real email to the venue's contact address (reusing `lib/email/send.ts`, the same infra every other transactional email in this app already uses) and logs it to the engagement's activity trail. Real two-way in-app threads are flagged below as backlog, not built now.
- "Mark onboarding complete" — sets `status = 'complete'`, `completed_at`, and is the moment a venue graduates from "staff-assisted" to a normal self-service venue in every other HQ view (Beta Command Center, Analytics) that currently has no way to distinguish the two.

**Explicitly deferred, not built in this pass (Backlog, per your own note that these get logged rather than silently expanding scope):**

## 3. Luv Success Guide

### 3.1 Build the Daily Briefing — as a reusable service, not a dashboard feature

Per the assessment, this is already fully designed (`docs/luv-platform-intelligence-architecture.md §4`) and needs exactly one new piece of infrastructure to unblock: a **"last observed state" persistence table** so the Briefing can compute "what got resolved since you last looked," not just "what's true right now."

**Decided 2026-07-22: the briefing is architected as its own service, independent of any single presentation surface.** The Dashboard card (below) is the *first* consumer of this service, not a feature with briefing logic embedded inside it — the same underlying briefing needs to be callable, unchanged, from Luv chat surfaces, onboarding, notifications, email digests, and future mobile experiences.

- **`lib/luv/briefing-service.ts`** (new) — a single `getDailyBriefing(venueId): Promise<LuvBriefing>` entry point returning the fully-composed, structured briefing (what needs you now / what's coming this week / what got resolved / what's informational) as data, with no rendering or channel-specific formatting inside it. Every consumer (Dashboard card, a future email digest, a future chat surface) formats this same structured result for its own medium — the service never returns pre-rendered markup or channel-specific copy.
- New table: `luv_observed_state` — `venue_id, observation_key (a stable identifier for a specific fact/risk/recommendation instance), first_seen_at, last_seen_at, resolved_at`. Computed by diffing the current observation feed (`observations.ts`'s existing output) against the previous snapshot on each briefing generation — this is the one piece of new persistence the whole capability needs.
- The briefing follows the already-designed four-part structure exactly — this plan does not redesign that structure, only builds it, behind the reusable service boundary above.
- **The Dashboard card is a thin presentation layer over `getDailyBriefing()`** — not itself where any briefing logic lives. It renders as a briefing/digest, explicitly not a chat interface, per the assessment's `guest-concierge.tsx` precedent: Luv narrates once per day/session, not a persistent input box inviting an open-ended conversation.

## 5. Cross-cutting technical decisions

- **RLS + explicit `service_role` GRANT in the same migration, every time** — non-negotiable per the assessment's own risk note; this exact class of bug has recurred multiple times in this engagement already.
- **New background/batch work (migration import jobs, Daily Briefing precomputation if needed) follows the Facebook Lead Ads processor's shape** — atomic claim, circuit breaker, backoff, dead-letter — not a bespoke synchronous loop like the current import wizard.
- **No new AI SDK dependency** — match the existing direct-`fetch` convention used by all 8 current Claude integrations.
- **No new "seen this" flag mechanism** — reuse the `onboardingDismissed`/`luvIntroSeenAt` boolean-column pattern for every new one-time-state need across all four pillars.

## 6. Suggested sequencing

Not a hard commitment — a reasonable dependency-aware order:

1. **Guided Setup foundation** (§1.1, §1.2), including the resumable-state table that both self-service *and* staff-assisted setup resumption (§2.2) depend on — this unblocks everything else, since Luv's setup-gap observations (§3.2), Luv's Success Library's setup-step links (§4.2), and staff's ability to resume a venue's setup all depend on this existing first.
2. **Migration Center + white-glove foundation together** (§2.1 items 1–3, §2.2 in full) — elevated from the original sequencing: the shared engine, dedup, batch tracking, and the HQ write-scoped RLS extension ship as one unit, per the 2026-07-22 decision that white-glove is launch-critical, not a fast-follow.
3. **Luv Success Guide's setup-gap wiring** (§3.2) — small, high-leverage, immediately makes Guided Setup feel proactive rather than passive.
4. **Luv's Success Library v1 content + distribution** (§4) — can proceed in parallel with 2–3, since it has no dependency on Migration Center.
5. **Migration Center's AI-assisted mapping + rollback** (§2.1 items 4–5) — the remaining, lower-risk half of this pillar.
6. **Luv Daily Briefing** (§3.1) — the single largest net-new build in the whole initiative; sequenced last so it can incorporate real Guided Setup and Migration Center observation sources from day one rather than needing a second pass to add them.

## 7. Decisions (resolved 2026-07-22)

1. **Journey framing starts at step 2.** A real (incomplete) venue row is created the moment the name is captured; the first micro-step stays generic, everything after is personalized. Determines exactly how early the DB row gets created (§1.2).
2. **Getting Started's visible step list is allowed to change.** It becomes a presentation layer over the Activation Engine's own gap data rather than an independently-computed 8-step list — fixes the two-systems-disagreeing problem for good, at the cost of the checklist looking different than it does today.
3. **White-glove migration ships together with self-service, not as a fast-follow — and is architected as one platform, two audiences** (role-based capability over a single shared engine), not two separate implementations. See the rewritten §2.2.
4. **Rollback is conservative and window-limited.** A batch is undoable only while nothing downstream has touched its records; once real activity happens, rollback is retired in favor of an honest "here's what changed" view. Matches this codebase's existing confirm-before-not-undo-after philosophy.
5. **Success Center authoring is DB-backed, editable without a deploy** — a real, if lightweight, admin content-management surface, not MDX files in the repo. See the rewritten §4.1.
6. **Naming: "Luv's Success Library"**, not "Success Center" or "Venue University." Renamed throughout this plan (§4).
7. **Daily Briefing's presentation surface is a Dashboard card, but the underlying briefing logic is architected as its own reusable service, decoupled from that card.** The Dashboard card is the *first* presentation surface, not the only one — the same briefing content needs to be callable from Luv chat surfaces, onboarding, notifications, email digests, and future mobile experiences without touching the underlying logic. See the rewritten §3.1.

All seven decisions are now resolved — nothing left open before implementation begins.
