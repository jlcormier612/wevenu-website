# Document Domain — Canonical Architecture Specification

**Date:** 2026-08-07
**Phase:** 2 — Architecture design only. Nothing in this document was implemented, migrated, or coded. It follows directly from Phase 1 (`document-management-architecture-certification-phase1.md`), whose finding — no canonical Document model, seven independent systems, working automation as the one proof unification is achievable — is the starting condition this design resolves.

**How to read this:** ten deliverables, each a clearly-labeled section below. Every decision is stated with its justification, not just its conclusion, so a future disagreement can be argued against the reasoning, not just the rule.

---

## 0. First Principle — What Is a Document?

> **A Document is any discrete, owned, identifiable unit of content — uploaded by a person, generated by the system, negotiated between parties, or produced by AI — that is created, exchanged, or retained in the course of operating a venue relationship, and that is capable of existing as a living record, a fixed representation, or both.**

Tested against every required case:

| Case | Fits because |
|---|---|
| Uploaded file (insurance cert) | Discrete, owned, identifiable; content and its one representation coincide. |
| Generated PDF (invoice) | Owned by the Business Object it represents; exists purely as a fixed representation. |
| Signed contract | Begins as a living, negotiated record; becomes a fixed representation the moment it locks. |
| Invoice | The financial record is a Business Object (§1); its PDF is the Document. |
| Insurance certificate | Submitted by another party, owned by the relationship it protects, never edited by the receiver. |
| Floor plan | The editor is a Structured Record (§1); its export is the Document. |
| Menu | Reference-behavior Document, static content consulted, not negotiated. |
| Proposal | Venue-authored living record before send; fixed once sent. |
| Questionnaire | Collaborative living record while open; fixed snapshot once submitted. |
| Attachment | Explicitly *not* required to be a full Document (§1) — a lighter reference that can be *promoted* to one. |
| Future AI artifact | A Document the moment a human retains, shares, or acts on it (§15); transient AI output that nobody keeps is never a Document at all. |

What is **not** a Document, by this definition: anything that is neither content nor a record of an exchange — a live, still-being-edited Structured Record (a floor plan mid-edit, a timeline mid-build) is not yet a Document; it becomes one only when exported into a fixed or negotiated content unit. A Business Object (a Contract's negotiation state, an Invoice's financial state) is not a Document either — it *produces* Documents. This split is the single most important decision in this specification and is expanded in §1 and §9A.

## 2. Canonical Document Entity Model

Not SQL. Seventeen properties, each with exactly one responsibility. Where two properties could be confused, the distinction is stated explicitly.

| Property | Responsibility | Explicitly distinct from |
|---|---|---|
| **Identity** | A permanent identifier for the Document as a concept — survives every version and representation change. | Storage path (which can change every version). |
| **Owner** | The single entity accountable for the Document's existence and lifecycle decisions. Exactly one (§3). | Actor (who performed a given action — an Audit fact, not a standing property). |
| **Source** | How the Document came to exist: Uploaded, Generated, Negotiated, AI-Generated. | Actor/uploader identity (a person can *upload* a Generated document's export; Source describes the *mechanism*, not the person). |
| **Type** | The business meaning — Contract, Invoice, Insurance Certificate, Floor Plan, Menu, Proposal, Questionnaire, Reference Guide, AI Summary, etc. Extensible without schema change. | Category tags/Metadata (descriptive, not structural). |
| **Status** | The Document's own current lifecycle position (§4) — independent of any Business Object's status. | Visibility (a Document can be Draft *and* already scoped to be private — Status is "where," Visibility is "to whom"). |
| **Visibility** | Who can currently see this Document. | Permissions (Visibility is current state; Permissions are the standing rules that govern how Visibility can change). |
| **Lifecycle** | The ordered states + transitions this Document's Behavior (§4) is allowed to move through. | Status (Lifecycle is the map; Status is the current pin on it). |
| **Versioning** | Whether/how this Document tracks prior versions of itself (§6). | Representations (versioning governs *when* a new Representation or new Document is created; it is not the artifact itself). |
| **Relationships** | The set of other entities this Document is linked to — exactly one Owner link, zero-or-more Reference links (§3, §5). | Owner (a subset of Relationships, singled out because it carries accountability). |
| **Storage** | A pointer to the physical Representation(s) backing this Document. | The Document itself (§9A) — a Document can exist with zero Storage pointers (still Draft). |
| **Metadata** | Free-form, Type-specific descriptive fields (name, notes, tags, expiry). | Type (Type is structural/behavioral; Metadata is descriptive and never drives lifecycle logic). |
| **Automation Events** | The canonical lifecycle transitions this Document Type emits (§7). | Audit (events are for other systems to react to; Audit is the permanent record for humans). |
| **Audit** | Immutable, append-only history of every action taken on this Document. Present for *every* Document, not just Contracts. | Activity (§13) — Audit is complete and internal-capable; Activity is the curated, human-facing subset. |
| **Sharing** | Explicit, revocable grants of Visibility to specific parties. | Visibility (Sharing is the *action*; Visibility is the *resulting state*). |
| **Retention** | The policy governing how long this Document (or its Representations) must be kept. | Archiving/Deletion (Retention is a rule; Archiving/Deletion are the transitions that rule can trigger or forbid). |
| **Archiving** | A reversible removal from active/default views. | Deletion (irreversible) and Supersession (implies a replacement exists — Archiving does not). |
| **Deletion** | Rare, permission-gated, irreversible removal. Never permitted for a Document that ever reached Finalized without first being Archived. | Supersession (Deletion removes; Supersession replaces while retaining history). |
| **Generation / Signing / Approval / Expiry** | Four independent optional capabilities a Document Type may or may not support (§4, §6, §9A). | Each other — a Document can support Approval without Signing (an internal checklist item) or Signing without Approval (a two-party contract with no internal review step). |

## 3. Document Ownership Model

**Canonical owner types — exactly five, nothing else:**

- **System** — platform-wide content with no single venue accountable for it (Terms of Service, Privacy Policy).
- **Venue** — content that exists independent of any specific relationship (a reusable template, the venue's own insurance policy, a blank requirements checklist).
- **Relationship** — the primary owner for anything spanning a couple's whole journey with the venue (most contracts, most invoices, the couple's Documents tab).
- **Event** — content specific to one occurrence (a floor plan for one wedding day, a day-of timeline export) — narrower than Relationship; a Relationship may in principle span multiple Events.
- **Vendor** — a vendor's own reusable Documents (COI, W-9, rate card), independent of any venue, because one vendor works with many venues.

**Explicitly *not* owner types — Contract, Invoice, Message, Task, Playbook, Staff Member, AI.** Each of these may *reference* a Document but never *own* one:

- **Contract / Invoice** — the signed PDF's owner is the Relationship/Event the Contract or Invoice itself belongs to, with a Reference back to the generating Business Object. Nesting ownership under a Business Object (Venue → Relationship → Contract → Document) would make "show me every document for this relationship" require walking every Business Object type; a flat Owner + References model keeps that query trivial.
- **Message / Task / Playbook** — the same reasoning: these are *conversations about* or *work referencing* a Document, not accountable parties for its continued existence.
- **Staff Member** — ownership implies accountability that must outlive one person's employment. A contract does not become orphaned when the coordinator who uploaded it leaves.
- **AI** — AI is a Source (§2), not an accountable party. An AI-generated summary is owned by whatever business entity it is about.

## 4. Document Lifecycle Specification

### 4A. Document vs. Representation (resolves §9A directly)

The living **Document** and its fixed **Representation** are separate concepts:

- **Document** — the product-level record: Identity, Owner, Type, Status. May hold live, still-changing content (a Questionnaire being filled out) or may have no content of its own at all (a pure upload, where content and Representation coincide).
- **Representation** — an immutable, point-in-time file generated or captured at a specific transition. Once created, **never** edited or overwritten. A Document may have zero (still Draft, nothing generated yet), one (a simple upload), or many Representations over time (a negotiated contract regenerating its current draft repeatedly).
- **Preview** — explicitly *not* a Representation. A thumbnail or first-page render carries zero trust weight, can be silently regenerated or discarded, and has no lifecycle implications.

**Invariant:** a Representation is never mutated. A change to a still-open Document produces a *new* Representation (old one retained, marked historical). A change to a Finalized Document never happens — see the Negotiated behavior below.

### 4B. Canonical States

One state machine; each Behavior (§4C) uses only the subset relevant to it.

1. **Draft** — content exists, owner-side only, not yet real.
2. **In Review** — submitted for internal approval before external Sharing (optional; only Types requiring Approval use this).
3. **Shared** — Visibility extended beyond the Owner side. ("Viewed" is an Audit event that can occur during Shared, not a separate state.)
4. **Pending Action** — a specific external action has been requested (sign, approve, submit) and not yet completed.
5. **Finalized** — the Document's content is now permanent: Signed (Negotiated), Approved (Submitted), Representation-produced (Generated), or Published (Reference).
6. **Superseded** — a newer Document has taken over this one's role; retained permanently, no longer current.
7. **Archived** — reversibly removed from active views; independent of Supersession.
8. **Deleted** — permission-gated, logically tombstoned; never available for anything that ever reached Finalized without first being Archived.

### 4C. Document Behavior Taxonomy — every current Type classified

| Behavior | Definition | Types | States actually used |
|---|---|---|---|
| **A — Collaborative** | Both parties edit the same living content. | Questionnaire (while open), Planning worksheet | Draft → Shared → Pending Action → Finalized (submission snapshot) → Archived |
| **B — Venue Authored** | Venue edits, client reviews. | Proposal, Invoice, Package* | Draft → In Review → Shared → Finalized → Superseded → Archived |
| **C — Negotiated** | Both parties revise; eventually locks. | Contract | Draft → Shared → Pending Action → Finalized (signed, permanent) → Superseded (by Amendment) → Archived |
| **D — Reference** | Never edited after publishing. | Venue guide, parking guide, alcohol policy, welcome packet, menu (static) | Draft → Finalized (Published) → Superseded → Archived |
| **E — Generated** | System-produced; no direct editing. | Invoice PDF, Signed Contract PDF, Floor Plan export, Timeline export, AI artifacts (once retained) | Finalized directly (skips Draft/Review) → Superseded (regenerated) → Archived |
| **F — Submitted** | Uploaded by another party; venue approves/rejects, never edits content. | Insurance certificate, business license, vendor COI, tax forms | Shared (on submission) → In Review → Finalized (Approved) or Deleted (Rejected) → Superseded (renewal) → Archived |

*\* Note on Package: reconsidered rather than accepted as given. A Package is more often a pricing/catalog **Structured Record** that a Proposal Document is *generated from*, not itself a Document — flagged here as a deliberate refinement rather than silently following the example. Where a venue genuinely authors a bespoke package write-up as client-facing content, that specific artifact is Behavior B; the underlying reusable Package catalog entry is not.*

*\* Note on Timeline: the prompt's own examples list "Timeline" under Collaborative and "Timeline Export" under Generated — this is not a contradiction once resolved through §1: the live Timeline is a Structured Record (like Floor Plan), and only its **export** is a Document (Behavior E). Surfaced explicitly because catching exactly this kind of overlap is what this phase is for.*

Every transition has exactly one owner-side actor responsible for triggering it — detailed per-role in §5.

## 5. Document Permission Model

Roles: Venue Owner, Manager, Staff, Planner, Client, Vendor, Guest, System, AI.
Actions: View, Upload, Replace, Delete, Share, Generate, Sign, Approve, Archive, Export.

| Role | View | Upload | Replace | Delete | Share | Generate | Sign | Approve | Archive | Export |
|---|---|---|---|---|---|---|---|---|---|---|
| **Venue Owner** | Own-venue Documents | Yes | Yes (pre-Finalized) | Yes | Yes | Yes | No¹ | Yes | Yes | Yes |
| **Manager** | Own-venue Documents | Yes | Yes (pre-Finalized) | Yes | Yes | Yes | No¹ | Yes | Yes | Yes |
| **Staff** | Own-venue Documents | Yes | Yes (pre-Finalized) | **No**² | Owner-approved only | Yes | No¹ | No³ | No | Yes |
| **Planner** | Assigned relationships only | Yes | Yes (pre-Finalized) | No | Owner-approved only | Yes | No¹ | No³ | No | Yes |
| **Client** | Own Documents (Shared+) | Yes (own uploads) | Own uploads only | Own uploads only | No⁴ | No | **Yes** (as named signer) | No | No | Yes |
| **Vendor** | Own + event-shared Documents | Yes (own library/event) | Own uploads only | Own uploads only | Yes (to assigned event) | No | **Yes** (as named signer, vendor agreements) | No | No | Yes |
| **Guest** | **None** | No | No | No | No | No | No | No | No | No |
| **System** | All (internal) | Yes (generation) | N/A | N/A | N/A | Yes | No | No | Policy-driven (retention) | N/A |
| **AI** | N/A — not an actor | N/A | N/A | N/A | N/A | Yes, only when System-invoked | No | No | No | No |

¹ Signing belongs exclusively to whoever the Document names as signer — never a venue-side role, even the owner, for a Document where the venue is the counterparty (a Contract is signed by the client; a vendor agreement by the vendor).
² Matches Phase 1's one confirmed-mature finding: delete is already correctly owner/manager-gated in the current `documents` table. Preserved and generalized here.
³ Approval of Submitted-behavior Documents (§4C) is deliberately restricted to Owner/Manager — a Staff member can flag a COI as received but not clear it as compliant.
⁴ Clients never Share — they can only respond to Sharing initiated by the venue (view, sign, upload their own). This preserves the venue as the accountable party for what leaves the building.

**Guest** is a deliberate, explicit exclusion, not an oversight: this domain governs trust-bearing business records; anything guest-facing (a seating chart display, a wedding website gallery) is a different concern outside the Document domain's boundary.

## 6. Document Versioning Specification

| Question | Answer |
|---|---|
| What creates a new version? | Any content change to a Document still pre-Finalized. Produces a new Representation under the same Document Identity. |
| What never creates a version? | Metadata-only edits (rename, re-tag, add notes) — mutate the Document record directly, logged as Audit only. |
| Can versions branch? | No. One linear chain per Document. Two alternative drafts are two separate Documents linked by Reference, not branches. |
| Can versions merge? | No — a human decision (pick one, Supersede the other), never a system operation. |
| Can signed versions change? | **Never.** Core trust invariant. |
| Can generated PDFs regenerate? | Yes, while pre-Finalized — produces a new Representation, prior one retained as historical. Once Finalized, regeneration is disallowed; re-download always returns the exact original Representation, never a fresh render from live data. |
| What happens to links? | A link to a specific Representation always resolves to that exact file, forever. A link to "the Document" resolves to the current Representation — which, once Finalized, is permanent. |
| What happens to audit history? | Fully retained across every version, append-only, never trimmed or overwritten. |

**Post-Finalization changes are never versions of the same Document.** A change to a signed Contract is a new Document (an Amendment), linked to the original via Reference, exactly matching real-world legal practice — you don't edit a signed contract, you draft an amendment.

## 7. Document Automation Specification

Canonical events — a strict superset of what Phase 1 confirmed is already correctly wired (`contract_signed`, `document_uploaded`, `document_uploaded_insurance`, `floor_plan_created`), generalized so that existing automation continues to work unmodified once systems migrate onto this model:

- **Document Uploaded** — qualified by Type (`insurance`, `contract`, etc.) at the event level rather than requiring a hardcoded second trigger string per category, as today's ad hoc pattern requires — a scalability fix, not a behavior change.
- **Document Generated**
- **Document Shared**
- **Document Viewed** *(included deliberately — read-receipts have real business value, e.g. "proposal viewed," matching standard CRM expectations, even though it's arguably "just" an Audit fact)*
- **Document Approved**
- **Document Signed**
- **Document Superseded**
- **Document Expired**
- **Document Archived**
- **Document Deleted**

Every event carries a consistent envelope — `documentId`, `type`, `ownerType`/`ownerId`, `actor`, `timestamp` — plus a Type-specific payload. This event set is what Playbooks, Tasks, and Notifications consume; it is deliberately the *only* place those systems learn about Document state changes, preventing the kind of untraceable, ad hoc wiring Phase 1 found (and preserving the one part of it that was already right).

## 8. Document Reporting Specification

**Document-domain-owned** (cross-relationship aggregates — "how healthy is my whole book of business"):

- Documents awaiting signature
- Expired insurance (list)
- Unsigned contracts (list)
- Documents shared today
- Most downloaded/exported documents
- Average signature time
- Document completion % *by Type*

**Relationship-domain-owned, sourced from Document facts** ("is this one wedding on track"):

- Missing required documents for this relationship/event
- This relationship's document completion %

**The line:** the Document domain exposes clean, queryable facts (Status, Type, Expiry, timestamps) for every Document it holds. It does not own "relationship health" as a concept — that aggregation belongs to the Relationship domain (or a future Reporting domain), consuming Document facts rather than Document domain reaching into Relationship logic. This keeps Documents a stable foundation other domains build on, not a domain that has to know about every consumer of its data.

## 9. Migration Strategy (Conceptual Only — No Implementation)

Direction and sequencing only; no migrations are written in this phase.

1. **Introduce the canonical Document + Representation concepts additively**, alongside every existing system, touching nothing that currently works. The existing `documents` table is the closest match and becomes the literal foundation — not replaced, extended.
2. **Cut over write paths one system at a time, most-mature first.** Contracts already have the richest lifecycle (draft/sent/signed + activity log) — migrating its "produce a Document on signing" path first proves the model against the hardest case early, not the easiest.
3. **Fold `couple_documents` and `vendor_library_documents` in as Owner variations**, not separate migrations — they were never architecturally distinct, only implemented separately (Phase 1, §1.4/§1.5).
4. **Leave Structured Records (Floor Plans) alone**; only their *export* path changes, to produce a canonical Document instead of (or in addition to) a `documents` row with `category='floor_plan'`.
5. **Leave Attachments (message attachments) alone**, as a permanently separate, lighter-weight concept — add the "promote to Document" action as new, additive capability, not a forced migration of every historical attachment.
6. **Consolidate storage last**, once every write path already goes through the canonical model — storage consolidation is purely an implementation detail (§2, Storage) and carries the least product risk to do last, after the domain model that governs access to it is already correct.
7. **Retire `couple_documents` and `vendor_library_documents` as read paths** only after every consumer (portal aggregation RPC, vendor library UI) has been repointed — deletion of the old tables is the very last step, not an early one.

## 10. Architecture Decision Record

| # | Decision | Consequence |
|---|---|---|
| ADR-1 | A Document and its Representation are separate concepts; Representations are immutable once created. | Signed contracts, paid invoices, and any Finalized artifact can never be silently altered — the trust invariant this whole domain exists to protect. |
| ADR-2 | Exactly five owner types: System, Venue, Relationship, Event, Vendor. Business Objects, Messages, Tasks, Staff, and AI reference but never own. | "Show me every document for X" is always a flat, single-level query, regardless of how many Business Object types exist above the Document layer. |
| ADR-3 | Business Objects (Contract, Invoice) are not Documents; they *produce* Documents. | Financial/negotiation logic stays in its own domain; Documents stay a stable, generic foundation other domains build on rather than a dumping ground for transactional state. |
| ADR-4 | Post-Finalization changes are always a new Document (linked by Reference), never a new version of the same one. | Matches real-world legal/financial practice; makes "was this ever altered after signing" an unanswerable-by-construction question rather than a policy someone has to enforce. |
| ADR-5 | Attachments remain a distinct, lighter-weight concept from Documents, promotable but not automatically equivalent. | Casual conversational file-shares don't inherit full audit/lifecycle overhead they don't need; the Document domain stays focused on records that matter. |
| ADR-6 | AI is a Source, never an Owner or an actor with standing permissions. Ephemeral AI output is not a Document until a human retains it. | Prevents an entire category of low-value, ungoverned "documents" from silently entering the system of record; keeps the human accountability chain intact. |
| ADR-7 | Generated Documents (invoice PDFs, signed contract PDFs) are first-class, not "merely downloadable." | They get full Audit and Automation participation — the exact artifacts most likely to matter in a dispute don't lose their trail. |
| ADR-8 | Guests have zero standing permissions in this domain. | Keeps the permission model's boundary honest; guest-facing concerns are explicitly a different domain, not a gap in this one. |
